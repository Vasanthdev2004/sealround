### Defensive security findings (2026-11-12)

- **Agent A, liquidity recovery.** The contract records an in-flight step before scheduling it (`contracts/fairground/src/liquidity.rs:797`). Both the normal continuation and the deadline recovery reject while the flag is set. A callback receipt that itself fails could leave bidder tokens locked. This is a conditional source finding. Add a recovery path that verifies DEX state and can safely run more than once before unlocking or retrying. **Resolved by agent A (2026-11-12).** A step in flight for 600 blocks (`STEP_TIMEOUT_BLOCKS`) is given up by the next `seed_liquidity` or `abandon_liquidity`, which first reads the exchange (`get_deposits`, then `get_pool_shares` or a page of `get_pools` from the pool count taken before `add_simple_pool`) and goes on from what is there. No pool is created twice and a deposit sends only what is missing. Each callback carries an `attempt` number, so a late or duplicate result changes nothing. Unit tests and sandbox tests (a lost deposit result, a lost pool result with decoy pools, concurrent seeds, concurrent abandons) cover it; the sandbox reaches a lost result by rewriting the record with `patch_state`, because no caller can make a callback fail (static gas reserved, checked before a step starts).
- **Agent A, liquidity evidence.** The successful add-liquidity callback can mark a pool seeded with zero recorded shares when the return value cannot be read (`contracts/fairground/src/liquidity.rs:563`).
